Pinned source: `46d8805d8556599eb0a6472892e67e3bb1e0de03` (tag v2.6.2). This is source inspection only; no builds or tests were run. Every source URL below pins the SHA. Paths/line numbers are in the checkout `/tmp/raptor-dolt-plan-evidence/dolt-source`.

## Findings for sc-runtime planning

**Latest scope ruling:** use a reusable `sc-dolt` adapter over existing SQLx/MySQL transport. Initial implementation requires branch-aware CRUD, branch create/list/delete/rename/checkout, merge, and the previously requested remote configuration/fetch/push/pull (including ff-only). Fork and clone are investigated but outside initial implementation. For merge conflicts, fetch diagnostic diff information from Dolt SQL/native APIs first; do not implement a diff engine or auto-resolution. Surface conflict evidence for an operator/user decision. Preserve provider/server scopes and SQL session permissions as part of the contract.

**Clone and fork are different concepts.** Dolt SQL registers `dolt_clone`, which clones a remote into a new database, with source URL and optional directory/branch/remote/depth/ref; server mode marks it AdminOnly. There is no `dolt_fork` procedure/function/table-function in the complete SQL registration lists. “Fork” appears in Dolt source as a graph fork point / forked branch concept, not as a separate provider API. Both clone and fork are outside initial implementation; do not imply a native fork endpoint or decide that fork maps to clone. Evidence C1-C3.

**Branch and data targeting:** branch procedure supports create, copy, rename (`-m`), delete (`-d`/`-D`), and upstream setting. It commits its transaction immediately and begins a new read-write transaction. Branch listing is `dolt_branches`; it is read-only and explicitly directs writes through `dolt_branch`. `dolt_add --branch` targets a revision-qualified database; normal DML is routed through the selected/revision-qualified database. Evidence C4-C6.

**Commit API:** `dolt_add` returns one BIGINT `status`; `dolt_commit` returns LONGTEXT `hash` (possibly no row for skip-empty); `dolt_commit_all` returns `(branch,hash)` rows. Commit preparation and permission checks are in the session; use one SQL connection/session per request and treat commit publication as an operation boundary. Evidence C7-C8.

**Remote operations and fast-forward:** `dolt_remote`, `dolt_fetch`, `dolt_push`, and `dolt_pull` are registered but remote/push/pull/fetch are AdminOnly in the external procedure registry. Push returns `(status BIGINT, message nullable LONGTEXT)`. Pull returns `(fast_forward BIGINT, conflicts BIGINT, message nullable LONGTEXT)`, and accepts remote plus optional ref; it rejects incompatible flags. `--ff-only` is implemented for merge and pull and fails without advancing when not possible; upstream tests assert both successful fast-forward and rejection/no data changes on divergence. Errors are not normalized to status rows consistently: parser/authorization/operation failures return SQL errors; push's implementation returns an iterator plus error, so consume the SQL response carefully. Evidence C9-C11.

**Merge/conflicts:** `dolt_merge` returns `(hash nullable LONGTEXT, fast_forward BIGINT, conflicts BIGINT, message nullable LONGTEXT)`. On conflict, use native diagnostics: `dolt_merge_status` gives source/source_commit/target/unmerged_tables; `dolt_conflicts_<table>` gives from_root_ish plus base/our/their column values and change types; `dolt_schema_conflicts` gives base/our/their DDL and description; `dolt_constraint_violations_<table>` gives violation type, row keys/values and JSON details. Preview pre-merge with `dolt_preview_merge_conflicts[_summary](ours,theirs[,table])`; query `dolt_merge_base(ours,theirs)` or `dolt_merge_bases(ours,theirs)` for base commit(s), since multiple best bases are possible. CLI `dolt conflicts cat <table>` is a native inspection route. Do not call `dolt conflicts resolve --ours/--theirs` or `CALL dolt_conflicts_resolve` automatically: those choose a side, and schema-conflict resolution tests are explicitly skipped because that SQL route is disabled. User/operator resolves after reviewing evidence. Evidence C12-C20.

**History and rollback:** SQL supports `dolt_reset`, `dolt_revert`, `dolt_cherry_pick`, `dolt_rebase`, `dolt_squash_history`, `dolt_stash`, and `dolt_tag`. Reset mutates working/index/head roots according to flags. Revert can generate several commits and supports continue/abort; cherry-pick is single-commit with continue/abort. These are supported upstream but reasonable post-V1 items after branch/commit/merge semantics are stable. Evidence C14.

**Backup lifecycle:** `dolt_backup` routes `add`, `remove/rm`, `sync`, `sync-url`, and `restore`; it is server AdminOnly, requires write permission, and `dolt_backups` lists configured backups. Restore clones into a new DB; backup sync has pruning. Include as a distinct operational capability, deferred from user-level version-control V1 unless product needs it. Evidence C15.

## Scoping, errors, transactions, streaming

Dolt procedure functions receive a MySQL SQL context and current DB/session; operations resolve database data from that session/provider. For a shared client crate, make server URL/auth and DB/branch explicit in request context. Use request-local SQL connections or transactions; do not share transaction state across concurrent requests. Branch procedure itself commits and restarts transaction. Most procedures are one-row `RowIter`; table functions and system tables stream rows via SQL result sets, and branch status/diff/log can be large. SQL errors carry provider/parser/auth failures; procedure schemas also encode operation status/conflict counts. Do not collapse errors into a single integer status.

Permission evidence: procedure registration carries `AdminOnly` metadata for clone/remote/fetch/push/pull/backup/gc/thread dump; operation bodies additionally check branch-control permissions such as Write or Merge. Since registry flags and operation checks coexist, a SQL principal may need both server admin capability and DB permission. An adapter should surface access-denied as typed SQL/API errors without retrying as data failures.

## Merge conflict diagnostic trace (initial behavior: inspect, then user decision)

1. **Before merge:** `dolt_preview_merge_conflicts_summary(ours,theirs)` gives per-table preview counts; `dolt_preview_merge_conflicts(ours,theirs,table)` is a read-only table function whose rows contain `from_root_ish`, `base_*`, `our_*`, `their_*`, side-specific diff types, and for keyless tables side cardinalities. Its docs say `from_root_ish` identifies the right-side commit/working set. Use `dolt_merge_base(ours,theirs)` for a base hash or `dolt_merge_bases(ours,theirs)` when reporting all best common ancestors.
2. **After merge conflict:** check `dolt_merge_status` (`is_merging, source, source_commit, target, unmerged_tables`), `dolt_status` (`conflict`, `schema conflict`, or constraint status), `dolt_conflicts` / `dolt_conflicts_<table>`, `dolt_schema_conflicts`, and `dolt_constraint_violations` / per-table violation table. The conflict table has typed base/ours/theirs values and `our_diff_type`/`their_diff_type` (`added|modified|removed`); it does not itself provide the destination/source commit IDs. Use merge status for source/target and log/ref resolution for the heads; calculate base(s) with merge-base APIs.
3. **Failure categories:** row conflicts are table artifacts with base/ours/theirs values; schema conflicts are separate table-level DDL conflicts with base/our/their schema strings and a description; constraint violations are detected/persisted separately with `violation_type` (`foreign key`, `unique index`, `check constraint`, `not null`), row data, and JSON `violation_info`. Merge procedure's generic conflicts count does not replace these detail APIs.
4. **Test proof (source assertions, not tests run here):** `dolt_queries_merge.go:853-912` constructs base value 0, diverges ours=1001 and theirs=1000, previews exact base/our/their rows, merges, checks `dolt_merge_status`, and checks the same tuple in `dolt_conflicts_test`. `:6343-6378` asserts schema conflict with base varchar(20), ours datetime(6), theirs int; `:387-438` asserts unique-index constraint violation details and clearing them after explicit row fix. These tests establish concrete observable diagnostics. `:1060-1084` explicitly marks schema-conflict `dolt_conflicts_resolve` coverage skipped because that procedure was temporarily disabled for schema conflicts.
5. **Native CLI route:** `dolt conflicts cat <table>` reads working-set conflicts and writes the table conflict view; use as an operator fallback when SQL inspection is inconvenient. `dolt conflicts resolve --ours|--theirs` is a deliberate mutation that automatically picks one side; keep it outside adapter automation.

## Merge conflict diagnostic trace (inspect, then user decision)

1. Before merge, `dolt_preview_merge_conflicts_summary(ours,theirs)` gives per-table counts; `dolt_preview_merge_conflicts(ours,theirs,table)` yields `from_root_ish`, `base_*`, `our_*`, `their_*`, side diff types, and keyless cardinalities. 2. 3. Schema conflicts are separate: `dolt_schema_conflicts` has `table_name, base_schema, our_schema, their_schema, description`. Constraint violations are separate: `dolt_constraint_violations_<table>` has violation type (`foreign key`, `unique index`, `check constraint`, `not null`), row key/value columns, and JSON `violation_info`. The merge procedure's conflict count is not sufficient diagnostic detail.
4. 5. Native CLI inspection fallback: `dolt conflicts cat <table>` prints working-set conflict rows. `dolt conflicts resolve --ours|--theirs` automatically chooses a side; keep it outside adapter automation. The SQL `dolt_conflicts_resolve` mutation is also deferred pending user/operator choice.

## Clean merge, conflict persistence, and transaction safety

**Priority:** branch creation and clean merges are initial requirements. Clean merge includes a divergent, no-conflict three-way merge; it is not limited to fast-forward. The ordinary `CALL DOLT_MERGE(source)` path executes fast-forward when possible, otherwise three-way merge, and on success creates the merge commit unless `--no-commit` is specified. Upstream test `dolt_queries_merge.go:1386-1420` asserts clean three-way merge returns `(hash,0,0,"merge successful")`, clean status, and a new log entry; `:805-841` shows `--no-commit` instead leaves merge state/staged change and no new log commit. `:766-802` shows explicit `--commit` on autocommit-off creates the merge commit.

**Target HEAD vs working set on conflicts:** the conflict branch does not create a merge commit. `performMerge` calls `SetWorkingSet` and returns the conflict result; only the no-conflict path calls `doDoltCommit`. Dolt's merge result may include nonconflicting changes applied to the target working root while leaving unresolved artifact rows on conflict tables; this is intentional partial merge working-set state, not the target HEAD commit. Example test `:2698-2720` shows conflict result with target table rows already containing both non-conflicting rows and duplicate-key rows, while the violations table explains invalid state. Therefore the adapter must distinguish “HEAD unchanged” from “working set unchanged.” Do not claim target working data is untouched on a conflict.

**Autocommit and conflict information:** with autocommit on and default `@@dolt_allow_commit_conflicts=0`, the SQL engine rolls back a conflict transaction on commit and reports `ErrUnresolvedConflictsAutoCommit`; docs instruct either disable autocommit and manually commit after conflict inspection, or enable `@@dolt_allow_commit_conflicts=1`. Test `:1551-1623` proves both paths: with the variable on, merge conflicts persist and are queryable; after disabling it, the same merge errors and the conflict table is empty because the transaction rolled back. A caller that needs persisted post-merge diff info must establish the compatible session setting/transaction protocol before calling merge. The pre-merge preview functions are read-only and useful for diagnostics without persisting a conflict working set, but summary preview only has `num_data_conflicts` and `num_schema_conflicts`; it does not report constraint-violation counts. Treat constraint outcome prediction as unavailable from this preview API.

**Rollback and abort:** generic SQL rollback clears uncommitted session roots (`dsess/session.go:1050-1055`), so it discards session-local, uncommitted working-set changes. It cannot reverse a merge commit already published by the successful default merge path; use a new revert/reset operation for that. `DOLT_MERGE('--abort')` is the native operation for an already persisted merge state; it calls `merge.AbortMerge`, sets the restored working set, then `CommitWorkingSet` (procedure lines 140-174). Upstream `:1551-1607` asserts abort returns main's original row and clears conflict/merge status. However, the pinned merge SQL suite does not include a direct `SET autocommit=0; CALL DOLT_MERGE(conflict); ROLLBACK;` test that then asserts both target HEAD and working rows. Source transaction code supports rollback of uncommitted roots, but add this as a required compatibility probe in the implementation; do not state it is tested. Also probe SQLx/MySQL autocommit behavior for the actual server/client sequence.

**TOCTOU:** preview and merge are separate SQL statements and do not share a preview token or immutable plan. `createMergeSpec` resolves refs when `CALL DOLT_MERGE` executes; `performMerge` checks source/target ancestry then executes. Callers must re-read/pin the source and target commit hashes around preview and reject/re-preview if either changed. Dolt's lower-level branch write paths include database concurrency checks, but the source/tests reviewed do not prove atomicity between separate preview and merge requests or a complete multi-client race contract. Required compatibility probe: race a target/source branch advance between preview and merge and assert no stale preview is represented as the exact outcome; verify target HEAD never regresses and conflict diagnostics match the actual merge commit pair. Do not add a custom merge algorithm.
