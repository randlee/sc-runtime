## Planning findings

- **Branch identity is SQL-session state.** For unqualified database names, Dolt resolves the session's last checked-out revision, falling back to the database default for a fresh session. `USE db/branch` selects an explicit revision database. See claims `branch-session-default-is-per-session` and `one-server-client-connection-gets-own-dolt-session`.
- **`DOLT_CHECKOUT` changes the SQL connection's active branch.** It updates that session's checked-out revision and current database; it does not alter the CLI checkout. Upstream CLI documentation requires a clean working set before checkout; the executed native probe on v2.6.2 instead succeeded with a dirty `main` edit, switched the active view to the target branch, and left the uncommitted change on the original branch working set (`dirty/main`). The adapter therefore must not assume checkout refusal on dirty working sets and must prefer branch-qualified `USE db/branch` or qualified table names when a dirty shared working set is possible. Pool reuse still needs explicit schema/branch reassertion or connection disposal. See `checkout-mutates-current-session-branch` and `probes/probe.md`.
- **CRUD can target a branch-qualified schema.** Existing tests cover INSERT, UPDATE, DELETE and DDL on qualified revision schemas, even while another schema is current. A branch-qualified schema can be writable, so it is not a read-only snapshot guarantee. See `branch-qualified-targeting-supports-crud`.
- **A branch and commit revision are different snapshot choices.** Commit/ancestor revision databases support stable historical reads. For Raptor's SQLite snapshot, resolve and record the branch's commit hash and enforce read-only access; do not treat a branch name as an immutable snapshot. See `branch-and-commit-revision-views-are-distinct`.
- **SQL `COMMIT` and Dolt commit history are separate concepts.** By default SQL `COMMIT` persists the working set; `dolt_transaction_commit` opts into creating a Dolt commit. Multi-branch/multi-database rules vary by this setting. See `sql-transaction-commit-is-not-necessarily-dolt-commit` and `multi-branch-and-multidatabase-commit-limits`.
- **Concurrent clients are supported with transaction conflicts.** Upstream tests exercise concurrent client contexts: same-branch write conflicts can yield deadlock/retry errors, while transactions have branch-specific visibility. Application code needs explicit retry/error handling. See `same-branch-concurrency-is-conflict-checked`.
- **Branch lifecycle has gaps for race planning.** Non-forced deletion checks other active sessions and rejects deletion of a branch they use. Forced deletion bypasses that check, and source comments note invalidating other sessions remains TODO. Duplicate branch creation is rejected, but I found no two-client creation race test. See `branch-deletion-scans-active-sessions-but-forced-delete-has-stale-session-risk` and `branch-creation-duplicate-is-rejected-but-race-not-tested`.
- **Prepared SQL evidence is real but incomplete for Raptor's exact path.** Engine suites have prepared transaction and revision database variants, and the MySQL client sample uses Go `database/sql` Prepare. SQLx is pinned at v1.3.4, but inspected SQLx use is in binlog replication helpers, not a wire test of branch routing through SQLx. See `prepared-statement-coverage-is-engine-level-not-sqlx-branch-proof`.

## Proposed Raptor contract to validate

Require a validated `(database, branch)` target for every CRUD operation. Either qualify every table as `db/branch.table` or pin a connection and establish `USE db/branch`; the former avoids dependence on mutable checkout state for table statements. Reject missing/unknown targets instead of silently defaulting to `main`. Keep SQLite reads pinned to a captured commit hash and read-only. Use pinned SQL connections or reassert and verify session state after pool checkout. Serialize or otherwise coordinate branch deletion against active application requests, and handle SQL transaction retry errors.

These are planning recommendations inferred from the cited implementation and tests, not existing Dolt guarantees beyond the specific evidence above.

## Transaction commit and concurrent working-set evidence

The following source and tests sharpen the commit contract. These are existing upstream test cases; this investigation did not run the suites.

- `dolt_transaction_commit=1` makes SQL `COMMIT` create a Dolt commit. At the storage publication boundary, Dolt submits the updated working set and optional branch-head update together through `CommitHeadUpdates` ([transactions.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/dsess/transactions.go#L329-L470)). `TestDoltTransactionCommitOneClient` verifies that SQL COMMIT advances HEAD and records `dolt_transaction_commit_message`; the concurrent test checks separate client messages and resulting history ([dolt_transaction_commit_test.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_commit_test.go#L36-L165), [concurrent case](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_commit_test.go#L220-L383)).
- `CALL DOLT_COMMIT` builds its pending commit from the current session's SQL transaction, publishes it through `DoltSession.DoltCommit`, and returns a commit hash ([dolt_commit.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/dprocedures/dolt_commit.go#L159-L218)). Existing tests run explicit commits amid two clients' concurrent writes and inspect WORKING versus HEAD ([transaction test](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_queries.go#L1981-L2109)).
- A Dolt commit does **not** indiscriminately sweep another client's prior SQL-COMMITted working-set-only edit into HEAD. In the concurrent transaction-commit test, client C commits row 4 to WORKING without a Dolt commit; clients A and B commit rows 2 and 3. HEAD includes A/B, while row 4 remains a HEAD-to-WORKING diff ([dolt_transaction_commit_test.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_commit_test.go#L220-L383)). Still, a branch working set is shared across sessions, and other clients' working changes may be visible; it is not a request-private staging buffer.
- Metadata is set through real supported interfaces: `dolt_transaction_commit_message`; session vars `dolt_author_name`, `dolt_author_email`, `dolt_committer_name`, `dolt_committer_email`; or `CALL DOLT_COMMIT` message and `--author` arguments. Name/email resolve from session vars, then SQL client, then configured identity ([variables.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/dsess/variables.go#L237-L305)). Tests verify transaction messages and explicit author/committer behavior ([dolt transaction commit test](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_commit_test.go#L151-L185), [commit metadata test](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_queries.go#L5398-L5416)).
- With autocommit on, enabling `dolt_transaction_commit` causes each subsequent write statement to create a commit. Upstream calls this permitted but not recommended; with autocommit off, multiple writes can be included in one transaction commit ([dolt_transaction_commit_test.go](https://github.com/dolthub/dolt/blob/46d8805d8556599eb0a6472892e67e3bb1e0de03/go/libraries/doltcore/sqle/enginetest/dolt_transaction_commit_test.go#L385-L430)).
- Dolt's internal optimistic retries address storage contention, not MySQL client transport retries. I found no upstream test that disconnects after durable publication but before COMMIT acknowledgement. Therefore the app must reconcile unknown outcomes using a durable operation marker before replay; the source does not establish exactly-once delivery.
