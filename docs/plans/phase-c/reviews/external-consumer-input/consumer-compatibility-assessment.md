## 1. Logging facade: useful additive seam, not upstream cleanup

At integration, `crates/sc-cron/src/lib.rs:165-183` exports Scheduler/WorkerHandle but not the receiver types; `scheduler.rs:288-292` accepts command-owned SharedCanonicalLog. `crates/sc-command/src/observability.rs:15-27` owns the actual trait and alias. `crates/sc-cron/Cargo.toml:27-30` already has a normal command edge with defaults disabled. Therefore a cron observability module reexporting the *same* CanonicalLog/SharedCanonicalLog/NoopCanonicalLog plus necessary canonical value/error types is a viable small additive facade: it removes the consumer's direct command declaration while retaining nominal trait identity and cron's transitive command dependency. `default-features=false` on cron does not eliminate normal transitive dependencies or undo features another dependency activates.

This does not remove the temporary cron-command edge. ADR-RUN-0017 (`docs/architecture.md:224-241,274-288`) requires separately proven upstream logging capability before eliminating that edge/trait/adapter. c-1 explicitly preserves that deferred cleanup (`sprint-c-1-consumer-runtime-contract.md:95-104`). Keep that distinction in the API/release decision. Do not invent a second receiver trait or silently switch nominal identities. Alternative: complete the separately qualified upstream observability cleanup; that has a larger compatibility proof and is not warranted by this consumer note alone.

Acceptance should use a truly separate crate with only cron/defaults-off as its SDK dependency, implement the receiver using cron's public path, exercise Scheduler::new_with_logger and actual events, and assert the reachable graph excludes clap/Axum/RMCP/server activation. A source import edit alone cannot close the consumer graph findings. Adding the facade also requires updating the existing cron public facade manifest, not weakening dependency guards.

## 2. Finite owned shutdown is a stronger contract than today

`scheduler.rs:887-903` explicitly documents that arbitrary synchronous stores/native code can exceed the deadline. `shutdown:904-948` times out the task and then still awaits it. `worker.rs:539-552` awaits an uncancelled spawn_blocking store operation. `store.rs:27-35` documents an open synchronous trait and the breaking consequence of adding required methods. The present behavior retains ownership, but cannot provide the consumer's finite total stop bound. Dropping/aborting the async wrapper or exposing only a task AbortHandle would lose ownership of already-started blocking work and does not fix it.

A shared dynamic operation context and independent stop control are reasonable API options; names in the external proposal are proposals, not existing APIs. The context must reach lock acquisition, SQL busy/progress work, row processing, transaction boundaries, and *every* scheduler/worker persistence/reload path. Store support must be explicit: an optional bounded entrypoint/capability with fail-closed admission can preserve existing unbounded implementations; a new required ScheduleStore method requires a breaking release. A generic wrapper with Self:Sized may fit today's generic scheduler but should be checked against any promised trait-object support and forwarding adapters. A wrapper that merely checks before/after an uncancellable operation is insufficient.

Define stop and cleanup budgets independently: T=0 can request immediate cancellation but cannot literally guarantee zero elapsed time to join actual work. State a finite cleanup allowance and what happens when unsupported native/foreign work cannot cooperate; current trusted Monty/native behavior cannot acquire a hard bound by assertion. Second-stop shortening must update shared state while the worker is awaiting a blocking call, and the expiry callback must run at expiry, independently of the owning join. Test held store mutex, each write/reload, active SQL and row decoding, second stop, T=0, idle/ordinary drain, no late writes/launches after release, generation fencing and rollback. Consumer process-tree/lease/connection-state obligations remain consumer-owned and need independent consumer QA.

This is new work under the current plan: `phase-c-plan.md:228-235` excludes new runtime features, c-3 is an RMCP/Utoipa migration preserving behavior, and c-3's owned paths include cron manifest/tests but **not cron source**. It needs explicit REQ/ADR/ownership/acceptance changes or a separate delivery path; listing REQ-CRON-0001 in front matter is not a blanket grant for new lifecycle semantics.

## 3. Windows Ctrl-Break

`shutdown.rs:53-64,94-102,126-135` stores/registers/polls only Ctrl-C. `builder.rs:320-326` installs signals before lock and later bind; this ordering is already correct for the currently supported listener. REQ-RT-0005 (`docs/sc-runtime/requirements.md:414-416,461-462`) requires Ctrl-C and explicitly leaves Ctrl-Break/console close/service stop open. This is an undecided capability, not an existing Ctrl-Break implementation regression.

If approved, register distinct Ctrl-C and Ctrl-Break listeners and poll **both** before lock/bind, retaining any already-observed event rather than short-circuiting the second registration/poll. Await either same retained listener afterward. Retain existing Unix/private-trigger semantics. Native Windows isolated tests should deliver real process-group Ctrl-Break both during coordinated startup and while serving/in flight, check clean exit/lock cleanup, and preserve the Ctrl-C scenario. A compile-only check does not prove console event behavior. No need for a new public signal abstraction or consumer-owned duplicate handler.

## 4. Cleanup-capable fixture without detached ownership

Production `builder.rs:234-285,320-345` already provides run_with_cleanup and invokes cleanup before dropping retained stores/instance/logger, including startup errors. REQ-RT-0005:427-449 requires that behavior for the fixture's same shutdown sequence. Yet fixture constructors `testing.rs:89-160` all call spawn, and `run_until_stopped:429-431` calls builder.run() (empty cleanup). Hence consumers cannot pass real background cleanup through the portable fixture. A start_with_cleanup seam can exercise production cleanup without process signals or public exposure of the private shutdown trigger.

Prefer additive start_with_cleanup with ordinary start delegating to the same internal runner using empty cleanup. Carry the callback/future into run_with_cleanup on the existing dedicated fixture runtime/thread (necessary Send/'static constraints), preserving startup health handshake, private root, error precedence, stop-on-failed-start, and thread join on explicit shutdown/drop. Decide whether logger/MCP combinations need a common configuration seam rather than proliferating incompatible constructors. Keep endpoint selection in sc-transport and private trigger private. Tests should prove callback once on normal stop and startup failure, stores/instance lock retained until callback completion, endpoint cleanup ordering, no detach on startup timeout, parallel fixtures isolated, and Windows-compatible operation. Existing joins intentionally await actual completion after reporting a missed budget; do not turn timeout into thread detachment.
