# d-11: generated-app-composition

## Description

### Deliverables
1. Wire real generated service/storage/cron in daemon/CLI/schema/config/hooks/wizard for SQLite/Postgres/MySQL and supported combined layouts. SQLite app data and cron rows default to one app file and the same SqliteDatabase/channel writer; remove cron.db/database_path and SQLx SQLite driver — REQ-RUN-0328; ANC-021/028/032.
2. Reject db=none+cron=true before generation. Invoke d-9 migration only on an explicitly supplied legacy cron file, preserving existing rows; no ongoing second cron database — REQ-RUN-0326; ANC-029.
3. Exercise actual CLI/HTTP/MCP read/write paths with real Python/Monty transforms and live claimed engines; update generation/getting-started docs and generation tests with the shipped0.3.0 interfaces — REQ-RUN-0201/0302/0702; ADR-RUN-0021.



4. Invoke d-3's single manifest checker on the real generated outputs; Every registry requirement in the template manifests changed here is >= its tested floor with no upper bound (ANC-037); no second checker or policy fixture set. Final recommended Cargo.lock and .sc-runtime/ metadata generation/delivery are d-12-owned.

### This sprint does not close
Nine-crate publication and actual upstream beads-cache migration/registry-only proof are d-12. This sprint runs development-source generated consumers and may not call them registry proof. No synchronization/code generator/config reload/unspecified permissions feature.
Monty selection is independent of cron: remove template feature coupling monty -> cron. Actual generated no-cron Postgres service executes a runtime-loaded Monty transform through sc-monty; cron-selected profiles use that same implementation and their JSON-enrichment command path. Preserve existing hook/integration tests. D-5 registers template service dependencies; this sprint owns daemon/CLI/wizard feature selection and real wiring (owner items 1/3/5/7).

After d-9's sc-cron-commands handoff and d-10's common helper delivery, integrate the complete user cron command set: cron.start and cron.end use storage_write; cron.list uses storage_read. A library-provided policy adapter delegates to existing CronStorage domain operations, retaining active-name, row-limit and generation checks; consumers need no app-written storage action. After d-3's completed daemon-manifest handoff, remove monty -> cron coupling in template/crates/daemon/Cargo.toml; a no-cron app selects sc-monty independently. No parallel edits to this manifest.

The complete cron command set is: cron.start uses storage_write; cron.end uses storage_write; cron.list uses storage_read. Every cron command uses the shared path. No cron command is excluded (ANC-053/054).

The sc-cron-commands handoff is source/tests/README only. Its dependency manifest remains d-9-owned until d-12 takes release-version lines; this sprint does not edit crates/sc-cron-commands/Cargo.toml and introduces no new dependency there.

In generated SQLite+cron profiles, application writes, cron command writes and scheduler persistence all use Storage<T> backed by the same SqliteDatabase instance, its single bounded write channel, dedicated writer thread and sole write-mode connection. Cron policy atomic operations submit through that same writer; there is no second SQLite write path. Preserve the d-9 scheduler operations and their existing tests (ANC-022/023/033).

## Acceptance criteria

req:REQ-RUN-0328/shared-storage — Live generated SQLite app+cron rows use the same database/handle, one writer owning its only write connection, per root writer constraints. Async callers await without blocking/spawn_blocking. cargo metadata/tree shows one patched libsqlite3-sys>=0.39 and no SQLx SQLite driver, for cron on/off and selected combined layouts; cargo deny check advisories clears target SQLite/rmcp advisories. Reader blocking_recv runs only on dedicated non-async worker threads with no runtime; async storage callers never block or use spawn_blocking to submit writes (ANC-027). Other engines implement shared Storage<T> without SQLite exposure unless selected.
req:REQ-CRON-0004/app-db — Preserve one active schedule per name, caller-supplied row limits including unlimited, stable IDs and per-row (id,generation) FENCED rejection; atomic set_enabled_many/replace_and_set_enabled remain all-or-nothing. Port actual two-process assertions with controlled process/channel barriers; preserve source crosswalk semantics. Populated cron.db migration retains every schedule field in app DB and reruns safely.
req:REQ-RUN-0326/layouts — db=none+cron rejected before any generated output; supported layouts render/build and actual cron uses app storage, no cron.db default setting.
req:REQ-RUN-0201/transforms — Actual CLI/HTTP/MCP service read/write runs the real Python/Monty transform; failures retain typed errors. Live SQLite/Postgres/MySQL services and selected combined layouts execute actual end-to-end procedures; no doubles stand in for engine/transport proof.
Required: just lint; just test; cargo build --workspace; sc-lint lint sc-boundary --root . --config sc-lint.toml; full generation unittest suite, tests/integration/storage-v2 live engine/transport procedures and target advisory checks on fresh generated resolves. Docs/links match actual generated APIs. No publication proof claimed.
Run the ONE shared async CronStorage conformance suite on actual generic SQLite/Postgres/MySQL providers through sc-cron CronStore; deterministic two-process providers port active-name/limit/fencing/atomic cases. Backends contain no CronRow type/schema/SQL. Legacy migration is d-9 app-owned code invoked by composition. Public storage failure/panic tests use typed Result semantics and real waiting callers, not a delay heuristic.
Full generated sqlite-postgres and sqlite-mysql layouts MUST resolve, build and execute with direct SQLx core/engine/macros dependencies selecting no SQLite feature, so no sqlx SQLite driver is in any graph, plus the patched rusqlite backend; current umbrella sets are known incompatible. Live query!/offline/migration behavior must pass, not inferred from lead cargo-check probe. Use cargo tree -i libsqlite3-sys (one selected>=0.39) and -i sqlx-sqlite (no selected package), never Cargo.lock. Existing CLI/daemon/schema/api-types tests are this sprint's owned regressions. Actual sc-lint#931 no-panic and transaction-body analyzer checks apply to changed template storage code; until delivered and passing, closure remains blocked. Record their actual commands and external state when available; runtime tests never substitute for static analysis.
req:REQ-RUN-0328/mixed-dependencies — Direct sqlx-core/engine/macros requirements select NO SQLite feature; cargo tree -i sqlx-sqlite selects no package in sqlite-postgres/sqlite-mysql too. Generated/production crates gain no sc-compose composition-crate or ATM dependency; sc-sha remains permitted, enforced by existing boundary lint (ANC-061/028).
req:REQ-CRON-0004/limit — The live shared app database refuses new schedule rows at the embedding app's configured row limit; exercise the ported case against real providers (ANC-031). The conformance suite executes the generic atomic multi-row operation on SQLite, Postgres and MySQL, proving all-or-nothing behavior (ANC-033).
req:REQ-RUN-0328/selected-native-tree — The cargo tree of EVERY selected layout (SQLite alone, cron on/off, sqlite-postgres and sqlite-mysql) contains NO sqlx SQLite driver crate. SQLx direct core/driver/macros crates are selected only for Postgres/MySQL; cargo tree -i sqlx-sqlite must select nothing in every case (ANC-028).
req:REQ-RUN-0328/generator-compatibility — Generation/setup instructions declare the repository sc-compose CLI minimum as >=1.8.0, using .sc/generation-tools.json as the source. Run the supported layout generation procedures with CLI1.8.0 and compatible CLI commands; generation succeeds at that floor. d-4 owns that declared tool requirement and executable-selection check; d-11 updates the layout instructions and generation tests using it (ANC-003/005).
req:REQ-RUN-0328/lifecycle — Using controlled shutdown and writer-failure signals, stop HTTP/MCP intake and scheduler work, drain/cancel in-flight work under the existing grace budget, await SqliteDatabase::shutdown and join its writer before releasing runtime/logger ownership (ADR-RT-0005). Every admitted write commits or returns a typed failure; writer failure stops intake instead of leaving a healthy-looking daemon. Use existing runtime shutdown control, not a new health endpoint.

req:REQ-RUN-0201/shared-interpreter — Generate Monty with Postgres and cron disabled, build and run its real transform, change source without rebuilding and observe the new value. A cron-selected generated app invokes cron.start/end through storage_write and cron.list through storage_read; these are all cron commands and none bypasses the shared path. The app modifies user JSON before persistence; sc-cron converts it to Monty values, never JSON strings, before passing it to hooks. Widget.create/delete use storage_write and widget.get uses storage_read; the direct-conversion example needs no hand-written transform or app-written storage action. No second Monty host is generated. Existing selected-layout and hook integration assertions remain in force.

req:REQ-RUN-0201/cron-integration — The actual generated app stores cron rows in its app SQLite file by default, rejects a second active schedule of the same name and a new schedule at the configured row limit through cron.start, and preserves fenced cron.end. Run the ported sc-cron-commands suite and generated CLI/HTTP/MCP integration on the same policy adapter. The generated usage docs state that Transform/storage_read/storage_write are provisional, not yet stable in0.3.0 (ANC-021/030/031/050).

req:REQ-RUN-0201/cron-submit — cron.start rejects non-compiling source at schedule write, before any tick, through the delivered sc-cron policy API; retain that assertion when routing commands (ANC-048).

boundary:cron-start-transform — For the implemented Phase D cron.start flow, the configured application Transform receives the script plus user JSON, may modify/append that JSON, and returns the row input before storage_write invokes the policy adapter/persistence. Transform/storage_read/storage_write remain provisional: this current flow does not prohibit later adding a second transform input, a typed Ok outcome with no write distinct from Err, or a transform inside an atomic transaction. Those three behaviors are not implemented in Phase D; the extensible seam delivered by d-10 preserves their later addition. A registered app transform is always awaited; the direct-conversion default is used only when no custom transform is selected and cannot bypass a selected transform. The test appends an application field and asserts the persisted JSON contains it; a transform error produces no write. d-10 tests the generic helper with its controlled storage double; d-11 exercises the real cron.start adapter and verifies sc-cron passes Monty values, not JSON strings, to the hook (ANC-055/043).
