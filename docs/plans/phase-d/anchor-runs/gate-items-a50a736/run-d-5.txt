# d-5: storage-contract

## Description

### Deliverables
1. Define the one shared sc-storage Storage<T> trait and its single AtomicStorage::transaction(spec, producer) operation for several row operations as one atomic unit; SQLite (d-6), Postgres (d-7) and MySQL (d-8) each implement that same contract (ANC-032/033). Define real std-only sc-storage Storage<T>, generic row/atomic transaction/error contracts and generic test doubles. No consumer table type, schema or SQL is in a backend (ANC-034). Prototype a fresh owned Send+'static future per retry; phase-d transaction properties are name and read-only/read-write (ANC-033); engine retry defaults do not preclude a later transaction-specific retry policy. Preserve measured transaction observations: name, queue wait, run time, row operations and outcome.
2. Freeze row descriptors with validated Identifier values, typed StorageError codes/retryability/source/recovery, and template WidgetStorage/OpenWidgetStore/StoresView extensions preserving existing create/get/delete (REQ-RUN-0201/0328/0330). Public storage functions return typed Results and never panic (ANC-035). Backend factory entry points are concrete inherent methods; sc-command owns Transform and plain storage_read/storage_write functions in d-10, with no StorageCommands or SqliteDatabaseFactory trait.
3. Define CronRow and an intentionally open CronStorage domain interface in sc-cron. CronStore wraps a backend Storage<CronRow>; it does not implement a public raw-write supertrait that bypasses fencing/name/row-limit policy. Declare the one shared generic double and conformance suite; d-9 implements cron policy once and owns its domain suite (REQ-CRON-0004/0005/0020/0021).
4. Register sc-storage and shared SDK/backend dependencies in root/template registries and boundaries including the cron Windows dev-dependency lines, with >= tested floors and no upper bound (ANC-037). Root owns rusqlite >=0.41. Make only the legacy SQLite API/dependency adaptations necessary for this contract branch's workspace build; the named files pass to d-9 for removal after contract sanity. Preserve existing legacy tests. Development remains0.2.0; release is coordinated0.3.0.
5. Amend REQ-RUN-0002/0702 and NFR-RUN-0009 for nine public0.3.0 crates and shared-storage typed errors; amend REQ-DBSQ-0001/0002 for sc-storage/Tokio plus the generic async writer surface; amend REQ-CRON-0001/0004 and NFR-CRON-0001 for sc-storage/sc-command/sc-monty domain policy and removal of direct cron rusqlite/Monty engine ownership. Amend ADR-RUN-0020/0021 with the exact tested contracts. Owner (randlee) ratification of the proposed extension/transaction/row/migration shape is PENDING: record it and change both ADR statuses to Active before this sprint closes or d-6..d-12 start. Synchronization and unspecified permissions remain deferred.
6. Record the existing one-checker interim rule in ADR-RUN-0005: d-3 owns it, d-11 uses it for generation, d-12 for unpacked archives/upload. Consumer=release reviewer; defect=restrictive SDK manifest defaults; remove after equivalent sc-lint#936 release and adoption. Record the approved nine-package tradeoff in ADR-RUN-0020: only SQLite gets the new published engine crate this phase; table-neutral Postgres/MySQL implementations remain generated, so fixes to that generated engine code require template updates/regeneration, not cargo update. Do not claim otherwise.

7. Deliver sc-monty in Wave 1 as the single Monty implementation, beginning with an exact copy of current sc-cron Monty code AND its unit and integration tests, passing before API extension. The exact baseline retains its existing dependencies until its copied unit/integration tests pass at a recorded commit before any API change. Preserve those assertions while separating cron/JSON adapters; at d-5 closure sc-monty production dependencies are only pydantic Monty crates; no sc-*, Tokio, serde_json, cron types or reserved cron names. It owns compilation, compiled sessions, resource limits, host dispatch, typed errors and session byte dump/load. Expose a compiled session and value-level MontyInvoke<Tin,Tout> (script, function name, inputs -> output); no new serialization framework. Move all interpreter machinery here; sc-cron, sc-command and generated services call it and contain no second host. Scheduler-specific adaptation and its integration tests remain in sc-cron, receiving Monty values rather than JSON strings. Register this ninth public crate in workspace/release/boundary inputs with open dependency floors; d-9 consumes it for hooks/cache and d-10 directly for transforms. — owner 2026-11-12 requirement change, item 1 and copy/single-implementation rulings.

### Boundaries and handoffs
No production storage engine or cron policy implementation, generated integration or publication; this sprint does deliver the independent sc-monty interpreter implementation. Real contract types/doubles compile and the workspace builds. Exact new transaction futures are prototype risk, not copied atm-core typed operations. D-6..d-10 consume the closed, ratified contract.
Register tests/support/storage and tests/support/cron-storage as allowed_test_double_paths in the relevant storage/cron boundary manifests and sc-lint configuration; these are private test support. Hand only each specific boundary facade file to d-6/d-9 after contract sanity. Convert sc-cron Windows dev requirements win32job >=2.0.3 and waitpid-any >=0.3.0 here; d-9 leaves those lines unchanged (ANC-037).

The real sc-monty crate code and its initial copy/tests close here before d-9/d-10 consume it. Register sc-monty in the template service registry without coupling its feature to cron; hand template service manifests to d-10 and daemon selection to d-11. The cache-specific MontyBlobRow belongs to d-9, not a generic engine.

The REQ/ADR amendments state the following contract, implemented by the named downstream owners: sc-cron saves each pre-run compiled session through Storage<MontyBlobRow>, keyed by sc-sha SHA-256(source) plus dump version; source in CronRow is authoritative and only a matching key may load. Missing/corrupt/version-incompatible/missing-hook blobs recompile from source and overwrite; schedule writes reject non-compiling source before a tick (d-9; ANC-044/045/046/048). Transform sources load from an app-owned UTF-8 file at invocation and can be replaced without rebuilding (d-10; ANC-049). Transform/storage_read/storage_write are documented as provisional0.3.0 and their signatures preserve later second-input, typed no-write and atomic-transform additions without building those options (ANC-050/051/052). Basic commands need only types, built-in plain conversion and Storage<T>, without an app-written transform/action; no REQ/ADR mandates hand-writing or forbids later consumer-side generation (ANC-056/057/058). Widget create/delete use storage_write and get uses storage_read. The complete cron command set is cron.start/cron.end via storage_write and cron.list via storage_read; none is excluded. Consumers may enrich JSON before schedule persistence (d-11; ANC-053/054/055/059/060/063).

The complete cron command set is: cron.start uses storage_write; cron.end uses storage_write; cron.list uses storage_read. Every cron command uses the shared path. No cron command is excluded (ANC-053/054).

## Acceptance criteria

boundary:storage-contract — Real exported row/storage/transaction/error/extension contracts and generic double compile; tests import production definitions, not replicas. Prototype verifies fresh owned retry bodies, atomic rollback on controlled Pending/error, exactly name/mode properties and controlled-clock transaction observations (ANC-033). Demonstrate multi-row-type support or the tested single-row-type limitation; if neither contract passes atomic/retry/safety cases, closure stays blocked.
boundary:storage-contract/ratification — Record randlee ratification and Active ADR-RUN-0020/0021 with the exact tested shape before closure. The named REQ/NFR amendments match the nine-package0.3.0 architecture. Future consumers never start against merely Proposed ADRs.
boundary:storage-contract/errors — StorageError exposes stable code, retryability, std::error::Error source and recovery guidance; mappings preserve those as typed cause/details without replacing existing domain error codes. Identifier construction returns typed errors and engines quote identifiers/parameterize values; descriptors contain no raw SQL.
boundary:storage-contract/workspace — cargo build --workspace and existing sc-cron legacy SQLite tests pass after necessary inherited rusqlite0.41 adaptations. Retain legacy assertions in the shared conformance suite. Generic test support contains no CronRow or domain policy; sc-storage is std-only.
Required: cargo test -p sc-storage; cargo test --manifest-path tests/support/storage/Cargo.toml; cargo test -p sc-cron; cargo test --manifest-path tests/contracts/storage-v2/Cargo.toml; cargo build --workspace; sc-lint lint sc-boundary --root . --config sc-lint.toml. Controlled unsafe-await/unmarked-helper/Pending cases stay separate from static proof; no implicit waiver.

boundary:sc-monty — First preserve an exact code/test copy, including existing integration tests, and run it before API extension. Cron-facing integration assertions run through the shared interpreter in d-9, not a replacement host. cargo test -p sc-monty and its README doctest pass; isolated cargo tree shows production dependencies only on the pydantic Monty crates, with no sc-*, tokio, serde_json, cron types or cron-reserved names.
