# d-9: cron-app-storage

## Description

### Deliverables
1. Implement CronStore<S:Storage<CronRow> + Storage<MontyBlobRow>> and CronStorage ONCE in sc-cron using the generic atomic unit. Implement only the domain CronStorage surface; keep the underlying Storage<CronRow> backend private and map its typed failures to CronError. Every public storage function implemented or changed here in CronStore/CronStorage, migration and cron-command storage adapters must return a typed Result and must not panic (ANC-035). Own CronRow mapping/schema, active-name/row-limit admission, per-row generation checks, fenced record_run/set_next/stop/disable and atomic set_enabled_many/replace_and_set_enabled — REQ-CRON-0004/0020/0021; ANC-030/031/033/034.
2. Migrate scheduler/worker to awaited app-supplied storage, porting hooks to the single sc-monty interpreter, preserving clock-driven tick dispatch, in-flight skip, cooperative stop/cancellation and typed FENCED behavior. Existing record_run and set_next still persist execution outcomes and next-run state through the fenced atomic policy operations in deliverable1. Domain read/check/mutate runs in one serializable atomic body, never separate calls. Backend is table-neutral — ADR-RUN-0013/0014/0020.
3. Implement legacy cron.db-to-app-DB migration above generic storage: preserve IDs/generation/run/end/spec/hook state; idempotent import and collision/rollback refusal. Legacy source is read only as explicit migration input, no ongoing second database setting — REQ-CRON-0004.
4. Reuse the ported async CronStorage conformance suite owned here against its double; port, never delete, existing assertions. Retire legacy DB files/dependency only after generic suite has equivalent case IDs and double tests pass. Actual engine/two-process provider runs are d-11, not a false double claim. Adapt thin cron-command APIs and READMEs — REQ-RUN-0702; ANC-061/035.


5. Ask sc-monty to compile the source when a schedule is submitted or updated, rejecting invalid source before any tick. Persist the just-compiled, never-run session blob through Storage<MontyBlobRow> in a sc-cron-owned table. Key it by SHA-256 of the exact source computed with permitted sc-sha, plus the Monty dump version. The schedule source remains authoritative; use a blob only for a matching key. Missing/stale/corrupt/unreadable-version blobs or missing cron_stop/cron_tick are cache misses: recompile from source and overwrite with the pre-run dump. Persist no run/session execution state. Migrate the new cron-owned table through generic row/schema APIs; no storage backend acquires cron SQL/types. — owner item 2.
6. Replace sc-cron's Monty compile/session/limits/host/dump/load implementation with calls to sc-monty. Keep JSON conversion, cron hook names/policy and schedule payload handling here; hooks continue receiving values, never JSON strings. Preserve all copied/ported unit and integration assertions. A schedule accepts Monty or Python script plus JSON data; keep that data available to the app transform before policy-checked persistence. — owner items 1/5, single-implementation and copy rulings.

## Acceptance criteria

boundary:sc-cron — Shared generic CronStorage conformance passes on the controlled double; scheduler hook/Monty/clock/cancellation and command-adapter regressions pass. All current behavior cases are ported, not weakened/deleted. Per-row FENCED, configured row limits, active-name and multi-row operations are implemented once through named generic transactions, with owned replayable inputs and transaction-safe bodies.
boundary:sc-cron/migration — Controlled legacy-row snapshot imports preserve every field; second invocation is idempotent, collisions/errors are typed and atomic. No default cron.db setting or store constructor. Public changed storage APIs are Result-returning/no-panic; no caller storage block_on/spawn_blocking bridge. READMEs match actual API; every registry requirement in sc-cron/sc-cron-commands uses >= its tested floor with no upper bound (ANC-037).
Required: cargo test -p sc-cron -p sc-cron-commands; shared conformance against double; normal Monty tests; cargo build --workspace at this closure; sc-lint lint sc-boundary --root . --config sc-lint.toml; sc-lint#931 no-panic rule and the external transaction-body analyzer must pass on this sprint's changed storage code once delivered; until both rules exist and pass, closure stays blocked. Record the actual rule versions and commands when available, never a fabricated pass or implicit waiver. This includes sc-cron CronStore/CronStorage, migration and changed sc-cron-commands storage adapters. d-11 executes same suite with actual engine providers and deterministic two-process scenarios; this sprint never calls the double real database proof.
boundary:sc-cron/row-limit — CronStore refuses to add a schedule row once its row count reaches the embedding application's configured limit; the existing row-limit tests are ported, not deleted (ANC-031).
boundary:sc-cron/atomic — set_enabled_many, replace_and_set_enabled and every domain read/check/mutate body call the shared generic transaction operation; several row operations commit or roll back as one atomic unit (ANC-033).
boundary:sc-cron/active-name — Within the SAME AtomicStorage::transaction body, CronStore rejects a second active schedule row with the same schedule name; retain and pass the ported active-name tests against the controlled double (ANC-030).
boundary:sc-cron/public-storage-functions — The public CronStorage domain operations (create/get/list_active, record_run/set_next/stop/disable, set_enabled/set_enabled_many/replace_and_set_enabled, query/context), migration and storage adapters all return typed Results and do not panic. These are the public storage functions governed by ANC-035, NFR-RUN-0009 and REQ-CRON-0005; exercise their typed-error paths through the shared conformance tests and actual sc-lint#931 rule, with no missing-rule waiver (NFR-RUN-0002).
boundary:sc-cron/ADR-RUN-0011 — sc-cron and sc-cron-commands production code, including CronStore/CronStorage, migration, scheduler/worker and cron-command adapters, calls no Runtime::block_on, Handle::block_on or futures::executor::block_on. Required: python3 scripts/adr_run_0011_grep.py crates/sc-cron/src crates/sc-cron-commands/src; non-test sources must contain no block_on call or allow-comment exemption. The only ADR-RUN-0011 exception is Runtime::block_on on the SQLite writer dedicated thread, which this sprint does not own.
boundary:sc-cron/policy-entry — No raw public CronStore write bypasses active-name, row-limit or fenced-generation policy; the same domain suite exercises all mutation entry points. Mapped StorageError retains typed code/source/recovery alongside stable CronError codes.
boundary:sc-cron/compiled-monty — Using the real shared interpreter and controlled storage, submit rejects non-compiling source; successful writes dump immediately after compile, before execution. Restart reloads an unchanged source/version blob without recompiling. Source/version mismatch, missing/corrupt bytes and missing cron_stop/cron_tick each trigger source recompilation and overwrite. Assert source remains authoritative, the key uses sc-sha SHA-256 plus dump version, and no post-run state is persisted. The new row/table and migration belong only to sc-cron, with no table-specific backend change. Port existing hook/host/limits/integration tests without weakening them; value inputs and JSON conversion behavior remain unchanged.

boundary:cron-manifest-floors — At closure verify every registry requirement in the complete sc-cron and sc-cron-commands manifests, including normal/dev/optional/target-specific entries, is >= its tested floor with no upper bound. Verify inherited Windows win32job >=2.0.3 and waitpid-any >=0.3.0 declarations too; prior d-5 ownership does not exempt them from this check. Those two already-open declarations remain unchanged. Use inspection evidence of the owned manifests; add no checking code, checker or dependency edge (ANC-037; owner one-checker rule).
